# TS codegen — two import-emission bugs surfaced in resolver pillar dogfood

**Date:** 2026-05-11
**Source:** archeglyph dogfood — resolver pillar first build attempt
**Status:** Bug report (not a proposal); both bugs reproducible from the committed `.spec.textproto` set in `.archegraph/specs/resolver/`
**Build:** archeglyph commit `f8ce3a8`, tag `resolver-pre-build` · archegraph vendored `27c3119`

---

## Context

First build of archeglyph's resolver pillar — the first un-built pillar
migrated to the v1.1 `.spec.textproto` authoring surface. 20 spec files,
greenfield-style (gcode has no resolver source yet). Compose was clean
(108 node deltas, 165 edge deltas, gcontract 568/1304); Phase 1 emitted
all 20 codegen files; Phase 1.5 scaffolded 17 barrel index.ts files;
pre_dag hung on a downed Docker daemon and the build was cancelled
before any agent runs fired. **Zero LLM tokens spent.**

While pre_dag was stuck, I inspected the Phase 1 codegen output in the
build worktree (`.archebuild/worktrees/archebuild-7713d1be-_dag/`).
Two distinct codegen bugs surfaced:

1. `Map<K, V>` resolves to a non-existent sibling directory instead of
   the TS built-in.
2. `InterfaceDecl` emits zero import statements regardless of what its
   methods reference. (StructDecl import emission is fine.)

Both are reproducible from the committed resolver specs. Build artifacts
are committed too (`dag.pb` / `gcontract.pb` / `gspec_delta.pb` under
`.archegraph/specs/resolver/`).

---

## Bug 1 — `Map<K, V>` treats TS built-in as spec-internal

### Spec input

`filtered_node.spec.textproto`:

```textproto
{ name: "tags",
  type: { named: { symbol: "Map", args: [
    { primitive: CHARACTER },
    { primitive: CHARACTER }
  ]}}}
```

The skill's TypeRef vocabulary explicitly lists `Map<K, V>` as a valid
shape (Named with args — "Nest for Map<K, V>, Vec<Option<T>>, etc.").
No registration of `Map` was made anywhere — there's no `external_package_imports`
entry for it, and no sibling spec declares a `Map` type. The expected
behavior is for codegen to recognize TS's built-in `Map` and skip emitting
an import (TypeScript's globals are always in scope).

### Actual emitted output

`packages/core/src/resolver/filtered_node/impl.ts`:

```ts
// @generated by archebuild — do not edit. Regenerated each build.

import { Localization } from '@archeglyph/proto/gen/content_pb';
import { Map } from '../map';        // ← bogus import — no such sibling exists

export class FilteredNode {
  id!: string;
  parentGroup?: string;
  tags!: Map<string, string>;
  label: Localization[] = [];
}
```

The sibling-directory fallback fired for `Map`, generating a phantom
import that will fail TS resolution at compile time. Affects every spec
that uses `Map<K, V>`: `filtered_node`, `filtered_edge`, `filtered_group`
(three files).

### Suggested behavior

A TS built-ins allowlist short-circuiting the sibling fallback for
`Map`, `Set`, `Promise`, `Date`, `RegExp`, `Error`, etc. — anything in
the TypeScript global scope that a user might reasonably reference
without import.

Alternative if an allowlist feels too special-case: surface this in
verify drift instead of silently emitting a broken import (the
sibling-directory fallback is described as "a diagnostic last resort —
produces an import that won't resolve, surfacing as a compile error" in
the skill, but for built-ins the resolver should know better than to
emit anything).

## Bug 2 — `InterfaceDecl` emits no import statements

### Spec input

`visibility_filter.spec.textproto`:

```textproto
file: "packages/core/src/resolver/visibility_filter/schema_gen.ts"

interfaces: [
  { name: "VisibilityFilter"
    methods: [
      { name: "filter"
        inputs: [
          { name: "request",
            type: { named: { symbol: "FilterRequest" } } }
        ]
        output: { named: { symbol: "archeglyph.util.Result", args: [
          { named: { symbol: "FilteredDiagram" } },
          { named: { symbol: "ResolveError" } }
        ]}}
      }
    ]
  }
]
```

Cross-references: `FilterRequest` (sibling spec), `Result` via FQN
(`archeglyph.util` → `@archeglyph/proto/util/result` per archebuild.yaml),
`FilteredDiagram` (sibling spec), `ResolveError` (sibling spec).

### Actual emitted output

`packages/core/src/resolver/visibility_filter/schema_gen.ts`:

```ts
// @generated by archebuild — do not edit. Regenerated each build.

export interface VisibilityFilter {
  filter(request: FilterRequest): Result<FilteredDiagram, ResolveError>;
}
```

**Zero import statements.** All four referenced types are unresolved in
the emitted source. Same shape on `style_cascade/schema_gen.ts` and
`token_resolver/schema_gen.ts` — three identical failures, one per
service interface.

### Contrast: StructDecl import emission is correct

`packages/core/src/resolver/resolved_node/impl.ts` (from the same build):

```ts
// @generated by archebuild — do not edit. Regenerated each build.

import { Glyph2D } from '@archeglyph/proto/gen/style_pb';
import { Localization } from '@archeglyph/proto/gen/content_pb';
import { NodeLayout } from '@archeglyph/proto/gen/style_pb';
import { Typography } from '@archeglyph/proto/gen/style_pb';

export class ResolvedNode {
  id!: string;
  parentGroup?: string;
  shape!: Glyph2D;
  typography!: Typography;
  layout?: NodeLayout;
  label: Localization[] = [];
}
```

Four FQN cross-package imports emitted correctly. The FQN-package
resolution path (the one wired in commit `27c3119`) is fine for
StructDecl — it's specifically the InterfaceDecl emit path that's
missing the import-collection step.

`filter_request/impl.ts` is also correct:

```ts
import { Diagram } from '@archeglyph/proto/gen/content_pb';
import { Stylesheet } from '@archeglyph/proto/gen/style_pb';

export class FilterRequest {
  diagram!: Diagram;
  stylesheet?: Stylesheet;
}
```

### Suggested behavior

Run the same import-collection pass on InterfaceDecl method signatures
(walking each method's `inputs[].type` and `output` recursively, same
as StructDecl walks `fields[].type`) before emitting the interface body.
Expected output:

```ts
// @generated by archebuild — do not edit. Regenerated each build.

import { FilterRequest } from '../filter_request';
import { FilteredDiagram } from '../filtered_diagram';
import { Result } from '@archeglyph/proto/util/result';
import { ResolveError } from '../resolve_error';

export interface VisibilityFilter {
  filter(request: FilterRequest): Result<FilteredDiagram, ResolveError>;
}
```

This bug is more severe than Bug 1 — Bug 1 affects three files with
one specific TypeRef shape (an easy hand-fix or allowlist patch); Bug 2
means **no service spec in TypeScript can produce a compileable
schema_gen.ts today**.

The canonical TS example (`examples/todo-api-brownfield/spec/todo_service.spec.textproto`)
ostensibly exercises this path, but its committed worktree at
`.archebuild/worktrees/archebuild-0a20e655-_dag/src/services/todo_service/schema_gen.ts`
shows the GENERATED output **does** have the imports correct:

```ts
import { ListTodosRequest } from '../../models/list_todos_request';
import { ListTodosResponse } from '../../models/list_todos_response';
// ...
```

So either:
- This regressed between when that committed worktree was generated
  and the current state of `archegraph` `main` (vendored at 27c3119), or
- There's something different about my spec set that triggers the
  empty-imports path. (No FQN-typed methods on the canonical example?
  Our `Result<T, E>` via FQN is the only obvious shape difference.)

Worth bisecting against the canonical example to check.

## Minor: pre_dag should have a timeout

Not a codegen bug, but worth noting: when Docker Desktop is down on the
host, archebuild's `docker compose run` step hangs indefinitely with no
progress logged. No timeout fires, no error surfaces. The user has to
notice via "nothing's happening" and manually `kill` the server.

A `default_timeout_seconds` is configured (600 in our archebuild.yaml)
and applies to per-node commands — does it apply to pre_dag? Apparently
not, or the docker-compose CLI's behavior of blocking on daemon-startup
doesn't surface as a timeout-able operation to the scheduler. Either
way: surfacing "pre_dag step has been running for N minutes with no
output" would help.
